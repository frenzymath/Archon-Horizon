# v0.1.1 — Lightweight Horizon

**Status:** draft / plan · **Branch:** `v0.1.1` · **Author:** Axel (+ Claude)

## 1. Vision

Stop shipping Horizon as an opinionated black box that reproduces "Archon". Make it a
**lightweight harness**: native Claude Code + a good interface + optional skills + MCP.

Two modes, one substrate:

- **Interactive (default human path).** Launch Claude in the workspace with **no preprompt**
  except *"load the `/horizon` skill, then wait for the user."* The user asks for whatever they
  want; the skill teaches Claude how to use Horizon's tools.
- **Automated.** A tiny supervisor loop runs repeated horizon sessions (see §5).

**The UI works the same in both modes** (§2.7). The only difference in interactive mode is that the
user can also talk to Horizon directly.

The `/horizon` skill lives in the workspace at `.claude/skills/horizon/SKILL.md`, is installed on
`init`, and is **user-editable** — self-healing on `init` but never clobbering local edits.

### Principles

1. **Push → pull.** The value is *state* (roadmap, DAG, inbox, memory), not preprompt prose.
   Deliver state through tools the agent pulls on demand; push only the thin `/horizon` skill.
2. **Git is the source of truth for progress.** Commit *message + diff* is the fine-grained
   progress record; the UI reads it from `git log`. Roadmap / task / inbox **reference** commits.
3. **Three concepts, distinct roles, no mechanical duplication** (§3).
4. **One ledger, sequential.** All commits go to `workspace.git`. **No harness worktrees** — an
   agent may create one for itself, but the harness only records commits in `workspace.git`.
   Sequential ⇒ a single committer ⇒ no index races.
5. **Raw git, not a wrapper.** The agent commits with plain `git` (wired to the ledger), following
   conventions from the skill — no `horizon commit` (§2.6).
6. **Resume, don't wait.** On a limit or crash the supervisor never sleeps waiting for a reset;
   it makes resume cheap and **account-agnostic** from logs + commits (§2.5).

## 2. Harness core

### 2.1 Only-preprompt = load the skill

Remove the composed preprompts (`compose_ground_prompt` / `compose_horizon_prompt` and the
standing-policy blocks in `agents/prompts.py`). The only injected system text becomes:

- interactive: *"Load the `/horizon` skill. Then wait for the user."*
- automated: the task directive + *"Load the `/horizon` skill."*

Anything load-bearing in today's preprompt moves **into the skill as readable reference**, not
pushed policy. The **one-shot / foreground discipline** ("you won't be re-invoked; block in the
foreground") is load-bearing and MUST survive into the skill.

### 2.2 The `/horizon` skill (the contract)

One editable skill that orients the agent:

- **Where you are:** workspace, projects, how to read the roadmap, DAG, inbox, memory (via `horizon`
  CLI — pulled, not pushed).
- **Picking work:** read the roadmap for global strategy + other projects' progress; pick the
  highest-value piece; or take the task the human launched.
- **Recording progress:** commit with plain `git` and a semantic, math-first message; update the
  roadmap for strategic progress; use the inbox to talk to future/other sessions.
- **Resuming (§2.5):** how to reconstruct state from `git log` + the prior session's log.
- **Git conventions (§2.6):** commits go to the workspace ledger; project `.git` is not used.
- **One-shot discipline:** block in the foreground; you are not resumed.
- **Delegation:** when to spawn a subagent (ground / janitor / reviewer) — optional, on judgement.

### 2.3 Supervisor loop (replaces the round engine)

Delete the mandatory H-G-H-G alternation in `orchestration/orchestrator.py`. Replace with a small
supervisor:

```
launch session → wait → classify exit → capture state → (relaunch | stop)
```

- **Sequential, one ledger, no locks, no worktrees.** Only one session runs at a time, committing to
  `workspace.git`. Parallelism is explicitly out of scope (§9).

### 2.4 No Ground role — cleanup is horizon-triggered

There is **no Ground agent in the loop at all** — not alternating, not scheduled. The horizon agent
is the only driver, and it spawns a cleanup subagent (janitor / work-reviewer / blueprint-reviewer)
**when it judges the work needs tidying**. The native subagents are already installed workspace-wide
(`install_subagents(workspace.root, …)`), so any horizon session can spawn them; the `/horizon` skill
tells it when/why. This is agent-triggered upkeep, not a timer.

### 2.5 Resume, don't wait (rate limits & crashes)

**We do NOT sleep until the limit resets** — that's risky. Instead we make the loss on any exit ≈ 0
and resume trivial from anywhere.

On any session exit (limit, crash, stop, done), the durable state is already on disk:

- **committed work** in `workspace.git` (+ diffs),
- the **session transcript / logs**,
- **roadmap / task / inbox** updates.

Because we use one real ledger (not a throwaway worktree), even *uncommitted* edits stay in the
work-tree — nothing is discarded. Skill convention: **commit early and often** to shrink the
uncommitted window.

On a rate limit the supervisor **stops cleanly and marks the run paused** (optionally: rotate to
another Claude account and relaunch immediately — §6 credential pool). Either way:

**Resume is cheap and account-agnostic.** A fresh session — same or different account, manual or
automated — reconstructs "what was I doing" from (a) recent `git log` + diffs, (b) the previous
session's log/transcript, (c) roadmap/task/inbox notes, all as instructed by the `/horizon` skill.
No session-resume, no account-bound state. The next session must therefore have **read access to the
prior session's logs and its commits** — that access is the whole resume mechanism.

### 2.6 Commits: raw git into one ledger (drop `horizon commit`)

Remove the `horizon commit` wrapper. The agent commits with plain `git`, which is safer (standard
tooling, no custom code path that can lose commits) and simpler.

- **Wiring so plain `git` "just works":** the session env points git at the ledger (e.g. export
  `GIT_DIR`/`GIT_WORK_TREE` for `.archon-horizon/vcs/workspace.git` with the workspace root as
  work-tree), so `git add/commit/status/log/diff` operate on `workspace.git`. Project `.git`
  directories stay neutralized ("we don't use `.git`" for projects).
- **Provenance without a wrapper:** a `prepare-commit-msg` / `commit-msg` hook in the ledger stamps
  `Archon-Run/Session/Task/Role` trailers from `ARCHON_HORIZON_*` env, so the UI still links
  commit ↔ session ↔ task. The agent writes only the semantic message; trailers are automatic.
- **Conventions in the skill:** `project-git` (already a skill) documents message style, that commits
  land in the ledger, and that project `.git` is not used.
- **Concurrency:** sequential + one ledger + one committer ⇒ the v0.1.0 index-race / phantom-SHA bug
  is resolved *by construction*; no commit lock is needed. (This supersedes the earlier "add a lock
  to `horizon commit`" fix.)

### 2.7 UI parity (hard requirement)

The dashboard, logs, roadmap, tasks, inbox, and commits/changes views read the **same on-disk state
regardless of how the session was launched.** The only behavioral difference is that interactive
mode lets the user talk to Horizon live.

Concretely: **interactive sessions must produce the same artifacts as automated ones** — the
transcript/logs captured to where the UI reads them, and commits in the ledger. Today
`commands/interactive.py` is a bare TTY with no transcript capture; it must be upgraded to capture
the transcript and emit the same run/session events an automated session does.

## 3. Data model — keep three concepts, kill the duplication

Not a merge. Each model keeps a distinct role; we remove the *mechanical copying* that produced the
"same comment in roadmap and task" problem.

### 3.1 Roadmap — *elevated* to strategic, cross-project, agent-maintained

- **Role:** the human's at-a-glance progress tracker **and** the agent's own record of progress +
  global strategy across all projects.
- **Change:** the horizon agent gets first-class **read + write** roadmap access in the skill (today
  only Ground writes it, the prover reads it 0×). It reads the roadmap to follow other projects; it
  updates its item's status/strategy as it works. Keep the hierarchy/outline view.
- Coarse status + strategy only — detailed progress is the linked commits (§4), to avoid churn.

### 3.2 Tasks — human-launched work + per-task tracking

- **Role:** the easy way for a human to launch a specific piece of work and watch *that one thing*.
- **Change:** a task's progress view is **derived from its commits** (via the `Archon-Task` trailer)
  plus a short status — stop copying commit prose into task comments.

### 3.3 Inbox — cross-session agent communication (kept)

- **Role:** how agents talk across sessions and projects. Legitimate and used. **Not** a human
  triage queue — we stop treating unread items as debt; the UI reflects them, humans glance.
- **Change (less mess):** the biggest noise genre (commit-SHA "did I really commit?" reports) is
  caused by the old commit path and vanishes under §2.6. Keep memory/protection channels + audience
  routing. Cap volume / auto-expire stale info items.

### 3.4 De-duplication actions

- **Delete `ensure_roadmap_task`'s field-copy** (`orchestrator.py:868-908`): a task and a roadmap
  item link by **reference** (`roadmap_refs`), never by copying title/summary/scope/metadata.
- **Delete the task→roadmap back-sync status comment** (`commands/task.py:140-176`).
- Progress narration lives in **commit messages**; roadmap/task/inbox carry references + short status.

## 4. Git as the progress record + UI

### 4.1 Principle

Commit message (semantic, math-first) + diff = fine-grained progress, read from `git log`.
Provenance trailers (stamped by the §2.6 hook) link commit ↔ run ↔ round ↔ role ↔ session ↔ task.

### 4.2 UI (proposed — react to this)

- **Logs page gets two modes:** *raw logs* (unchanged) and a *progress* mode that shows each
  session's **commits as distinctive cards** inline in the session timeline — message + touched
  files + expandable diff. The commit template is visually distinct from log lines.
- **Left panel:** a per-session commit summary (count + titles), click through to the cards.
- **"Changes" view → commit-granular.** Upgrade today's changes view to per-commit diffs, reachable
  from a session, a task, or a roadmap item — sourced from `git log`, not events.
- **Roadmap / task detail:** list the **linked commits** (by trailer) instead of re-narrated comments.

## 5. Automated mode

**Decided:** automated mode = N rounds of **Horizon-only** sessions, no Ground role. Cleanup is
**agent-triggered** — the horizon agent spawns a janitor/reviewer subagent when it judges the work
needs tidying (§2.4), not on a schedule. `horizon run <target> --supervisor --rounds N`. Stops
cleanly on a usage limit; state on disk, re-run to resume (§2.5).

## 6. New functionality — candidates (pick / cut)

- **Credential pool** — rotate to another Claude account on a rate limit instead of pausing; the
  primary alternative to waiting (§2.5). **Check Anthropic ToS first.**
- **Cross-project progress digest** — auto-generated from roadmap + commits; the "where is
  everything" view the elevated roadmap enables.
- **Per-session "why I stopped / what's next"** surfaced from the last commit + log.
- **Metrics over time** — proved declarations, sorries remaining, DAG coverage — as trend charts.
- **Pause/finish notifications** (push) when a run pauses (limit) or completes.
- **`/horizon` skill profiles** — e.g. aggressive vs careful presets the user can switch.

## 7. Sequencing

- **Phase 0 — Commit path.** Drop `horizon commit`; wire the session so plain `git` targets the
  ledger; add the provenance `commit-msg` hook; document conventions in the `project-git` skill.
  *(Independent; dissolves the v0.1.0 serialization bug.)*
- **Phase 1 — Skill + no-preprompt + UI parity.** `/horizon` skill; interactive launch with only the
  skill; upgrade interactive to capture transcript/events (§2.7). A/B against the current heavyweight
  flow on one real project before deleting anything.
- **Phase 2 — Supervisor.** Supervisor loop + resume-from-disk (§2.5); Ground → subagent; delete the
  round engine + all locks.
- **Phase 3 — Data-model dedup.** Delete `ensure_roadmap_task` copy + back-sync comment; give the
  horizon agent roadmap read/write access.
- **Phase 4 — Git-progress UI.** Commit cards in logs, commit-granular changes, linked commits on
  roadmap/task.
- **Phase 5 — Cleanup.** Remove dead prompt composition + the `horizon commit` command; update docs/tests.

## 9. Explicit non-goals

- Not merging roadmap/task/inbox into one table — they stay distinct concepts.
- Not removing the inbox or the roadmap.
- **No harness worktrees**; commits only ever go to `workspace.git`.
- **No `horizon commit` wrapper** — plain `git`.
- **The supervisor never sleeps waiting for a rate-limit reset.**
- No parallel sessions in the harness (sequential only); no multi-account by default (§6, ToS-gated).
