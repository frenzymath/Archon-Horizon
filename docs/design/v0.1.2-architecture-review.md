# v0.1.2 — Architecture review & consolidation plan

**Status:** draft / review · **Branch:** `v0.1.1` · **Author:** Claude (full-codebase review, 2026-07-16)

> [!NOTE]
> **Historical document.** This is a point-in-time planning note from before
> v0.1.2 was implemented, kept for rationale. It is not maintained and some
> proposals here were changed or dropped during implementation — notably,
> `hgraph` ended up **vendored in-tree** under `src/archon_horizon/hgraph/`
> rather than taken as an external dependency. For how the system works now,
> see [the current guides](../README.md).

This is a whole-codebase review after the v0.1.1 phases (0–5d) landed. It answers three
questions: *how does the system actually work now*, *what is dead or duplicated*, and *what
should v0.1.2 do* to finish the "lightweight harness" vision — a set of tools plus a skill
that explains intent, robust to rate limits, engine-agnostic (Claude Code + Codex).

---

## 1. How it works today

### 1.1 The two execution paths

**Interactive (`horizon run --bare`, `--backend interactive`)** — `commands/run.py:251`
launches the engine as a TTY session via `commands/interactive.py`. `--bare` seeds only
*"load the `horizon` skill, then wait"* (`horizon_seed_prompt`, `interactive.py:435`). A
background tailer (`_InteractiveTailer`, `interactive.py:219`) mirrors the engine's own
on-disk session file into a canonical `transcript.jsonl`, so interactive sessions appear in
the dashboard identically to automated ones (UI parity, design §2.7 — done).

**Automated (`horizon run <target>` / `--supervisor` / `--resume`)** — `commands/run.py:65`
builds the `Orchestrator` (`config/loader.py:build_orchestrator`) and calls `orch.run()`:

```
for round in rounds:
    queue focus → write parser DAGs → scheduler selects QUEUED tasks
    for task: _horizon_step:
        compose HEAVYWEIGHT prompt (agents/prompts.py)        ← still the old path
        CommandHarness.run:  claude -p --output-format stream-json  |  codex exec --json
            stream stdout → engine parser → transcript.jsonl (live)
            classify failure (regex) → retry transient w/ backoff
        agent owns terminal status via `horizon task set`; else task → QUEUED
        integrate session → one ledger commit (vcs/integration.py)
    publish (rich leandag DAGs) → "system" session bookkeeping
    stop on: fatal failure (auth/usage-limit/aborted-early) | no tasks | focus complete
```

`--supervisor`, `--run <role>`, and the plain focused run all reduce to `orch.run()` with a
`RunRecord` — they are the *same* engine, not a new lightweight loop (design §2.3 — **not
actually done**; the flag exists, the small supervisor does not).

### 1.3 What already matches the light-harness vision

Worth naming, because the refactor is smaller than it looks:

- **The tool layer exists and is engine-agnostic**: the `horizon` CLI (`inbox`, `roadmap`,
  `task`, `leandag`, `search`, `--json` everywhere) + the `lean_search` MCP + `hgit`.
- **The skill exists** (`skills/horizon/SKILL.md`) and is the designed contract.
- **State is pull-able**: everything the old prompt pushes (roadmap, inbox, memory,
  protections) is readable via the CLI.
- **Resume-don't-wait works**: on-disk state + ledger + `--resume latest`; native
  `claude --resume` recovery with fresh-session fallback (`harness_agents.py:184`).
- **Failure classification + halt** exists (`command.py:46`, `orchestrator.py:95`): transient
  errors retry with backoff; usage/auth limits stop the run cleanly.

## 2. Findings

### 2.1 The v0.1.1 migration is half-landed (the main mess)

1. **Automated runs still use the heavyweight composed prompt.** Design §2.1 said the only
   injected text becomes *task directive + "load the `/horizon` skill"* — but
   `compose_horizon_prompt` (`agents/prompts.py:360`) still pushes role prose, skills list,
   subagent catalog, roadmap slice, inbox, memory, protections, report guidance
   (~400 lines of composition code). Only `--bare` interactive got the new seed. This is
   the single highest-leverage remaining change.
2. **The supervisor was never built.** `--supervisor` (`run.py:176`) is a comment plus the
   old round engine. `_run_supervisor`, `_run_single_role`, and the default path are three
   spellings of the same `orch.run()` call.
3. **Ground removal fallout** (agent-visible, so it actively confuses sessions):
   - `skills/subagents/SKILL.md`, `skills/horizon-inbox/SKILL.md`, `subagents/base.py:125`,
     descriptors `work-reviewer.md`/`blueprint.md` still describe an *active* Ground agent —
     directly contradicting `skills/horizon/SKILL.md:76` ("no separate Ground agent").
   - `horizon run ground` is documented in help text (`run.py:530`, `run.py:102`) but
     `ROLE_TARGETS = ("horizon",)` — it now falls through and errors as an unknown target.
   - Dead config: `roles`, `start_with`, `end_with`, `ground_subagents`,
     `subagent_harness`, `references.transcription` (+ its two resolver properties) are
     parsed and validated but never read (`config/schema.py:242–352`).
   - Dead files/branches: `agents/prompt_templates/ground.md`, `ground_write_domain`
     import in the orchestrator, `ground.failed` event rendering, `"[ground]"` log line
     (`orchestrator.py:359`), stale `--upkeep-every` comment (`run.py:106`).
   - `cfg.ground_harness` is half-alive: only `discuss` and `horizon subagent` use it.
4. **Lock removal fallout**: `integration.py:44–133` still carries the full cross-process
   commit-lock stack (`_workspace_commit_queue`, stale-lock reclaim, pid/host checks) that
   Phase 5b's rationale made unnecessary — and it still runs on every commit. Server-side,
   `live_run_id` is threaded through `_runs_state`→`_run_state` but is permanently `None`
   (`service.py:317–370`).
5. **`horizon commit` removal fallout** (dead, test-only survivors): `project_checkpoint`
   (`integration.py:279`), `ProjectGit`/`project_git_for`/`collect_revisions`
   (`git.py:628–695`), `WorkspaceGit.session_commits` (`git.py:430`), git-notes
   `add_note`/`read_note` (`git.py:603`).

## 3. v0.1.2 — finish the light harness

### 3.1 Endgame picture

A workspace is a **self-orienting environment**; the harness is a **thin supervisor + tools**:

```
workspace/
  CLAUDE.md, AGENTS.md      ← 3 lines each: "load .claude/skills/horizon/SKILL.md"
  .claude/skills/…          ← the contract (intent), user-editable
  .claude/agents/, .codex/agents/   ← compiled subagents (unchanged)
  .archon-horizon/…         ← state, pulled via `horizon` CLI (the tools)
supervisor: loop { launch engine session → classify exit → stop|relaunch }
```

**Engine-native orientation.** Claude Code auto-loads `CLAUDE.md`; Codex auto-loads
`AGENTS.md`. Have `init` write both as a 3-line pointer to the horizon skill (+ the
one-shot discipline sentence). Then *even the seed prompt* shrinks to the task directive —
and the skill genuinely loads on both engines without engine-specific plumbing.

### 3.2 Kill the composed prompt (design §2.1, for real)

- Automated prompt becomes: task directive (title/objective/id) + "load the `horizon`
  skill" + the resume nudge when resuming. Delete `agents/prompts.py` composition,
  `prompt_templates/`, `install_prompts`, and the `<state_dir>/prompts/` install.
- Move the two load-bearing pieces that aren't yet in skills into them:
  the **report shape** (`## Progress` / `## Why I stopped`) and the **subagent model-tier
  economy** paragraph (into `subagents` skill). One-shot discipline and status ownership
  are already covered (`horizon-waiting`, `task-status`).
- A/B on one real project before deleting (the doc's own Phase 1 rule).

### 3.3 Shrink the orchestrator into the supervisor (~200 lines)

Keep: task as the unit of focus, agent-owned terminal status, per-session ledger
integration, resume from disk, fatal-failure halt. Retire with care:

- **Scheduler/round machinery** → `for i in range(rounds): run one session on the focus`
  (that is what actually happens today with `max_parallel_sessions = 1`).
- **Write-domain enforcement + freeze rules** → the inbox `protection` kind is the designed
  soft-freeze; the glob write-domain flagging duplicates it for a constraint nobody acts on.
  (Keep the *event* if you want the audit trail; drop the WriteDomain plumbing.)
- **Task-terminal watcher thread** (`_task_terminal_watcher`) → poll between sessions, not
  during; closing a task mid-session is rare and the session's commit is durable anyway.
- **System-session buffering** (~150 lines) → keep if you value the Log attribution;
  otherwise emit plain events and let the UI group them.
- Collapse `--supervisor` / `_run_single_role` / default into one focus-building helper.

### 3.4 Consumption awareness (new, engine-agnostic)

The stream parsers already extract per-message usage for both engines. Add:

1. **Live `usage.json` per session**: in `CommandHarness._stream`, fold USAGE events into a
   running `Usage` and atomically rewrite `<session_dir>/usage.json` (tokens in/out/cached,
   cost, elapsed, events seen) every few seconds.
2. **`horizon usage` CLI**: resolves the current session via `ARCHON_HORIZON_SESSION`/`_RUN`,
   prints session + run totals, and — when a budget is configured — remaining headroom.
   `--json` for the agent. Works identically under Claude and Codex because it's just the CLI.
3. **Optional budget config**: `workspace.budget: {session_tokens_out, run_cost_usd}` —
   supervisor checks between sessions (stop cleanly like a usage limit); the skill tells the
   agent to check `horizon usage` before fanning out subagents or starting a huge build.
4. **Rate-limit weather**: recent `failure_reason`s are already in run state; surface them in
   `horizon usage` ("2× rate_limit in the last hour → prefer small models / fewer subagents").

This keeps the *mechanism* in the harness and the *policy* in the skill — matching push→pull.

### 3.5 Rate-limit robustness

Keep resume-don't-wait. Three upgrades:

1. **Structured classification before regex**: Claude's final `result` stream event and
   Codex's error events carry typed error info the parsers already see — classify from
   those first; keep `_FAILURE_PATTERNS` as the fallback for unstructured stderr.
2. **Honor advertised retry windows**: when the error text carries "retry after Xs" /
   "resets at …", use it to cap the backoff or stamp it into the pause marker so
   `--resume` tooling (cron, a human) knows when relaunching is worthwhile.
3. **Pause marker on limit-stop**: on `usage_limit`, write `runs/<id>/paused.json`
   (reason, reset hint, focus) and exit with a distinct code — makes external relaunch
   loops trivial without the supervisor ever sleeping.

## 4. HyperGraph adoption — replace leandag (and eventually the parser stack)

`hgraph` (same author) is a plain-files semantic graph for
autoformalization: one Markdown file per node (YAML front-matter + math body), one file per
edge, git-versioned, no database. It is a strictly better fit than the vendored leandag:

- **Typed edges**: hard `uses` (the schedulable DAG) + soft `formalizes` (informal↔formal
  identity; union-find collapses a concept's tex + Lean forms into a supernode) +
  `related_to`. Chapters, semantic `group`s, and `level` granularity on top.
- **Per-node progress at node scale** (the ask): agents/humans attach `comment-N.md` and
  two-axis Maths/Lean `review-N.md` files *with* the node (`hgraph add comment/review
  --author agent`, `--json` everywhere), and `hgraph modify node --set status=…` for
  metadata. Failure memory lives with the node.
- **Computed closure state** over the hard DAG (`closed / ready / formalized_open /
  blocked`) and `hgraph frontier` ranking "prove this next" by downstream unlocks —
  exactly what the horizon skill's "pick the highest-value work" step needs.
- **`lean_status` is derived from scanning the Lean**, not from trusting `\leanok`.
- **Sync consumes the same inputs** leandag does (leanblueprint `.tex` with `\input`
  recursion + `.lean` sources), is idempotent, and never touches authored fields.

### 4.1 Integration plan

1. **Depend on `hgraph` as a Python library** (`Graph.open()`, `Analysis`, `frontier()`)
   — both projects are Axel's; pip/git dependency, not vendoring.
2. **Thin adapter (~50 lines)** `blueprint/hgraph_graph.py`: `Graph` + `Analysis` →
   Horizon's `{nodes, edges, dangling, meta}` dict, replacing `leandag_graph.py`.
   Watch the conventions: hgraph edge direction is `a --uses--> b ⇒ b ancestor of a`
   (verify against Horizon's `dep → dependent`); node ids are 12-char sha1 (address by
   `label:` / `decl:`); synthesize `dangling` from `stale: true` + unresolved-target
   sync warnings; filter soft edges out of `edges` (or carry them in `meta`).
3. **Agents use the `hgraph` CLI directly** — retire `horizon leandag` (and the `leandag`
   skill) in favor of a short `hgraph` skill. Fewer wrappers = the light-harness rule.
   The orchestrator's per-boundary refresh becomes `hgraph sync` instead of
   `workspace_dags_rich`.
4. **Delete the vendored `leandag/` package** (~2,900 lines; exporters/queries/reporter
   already have zero consumers) once the adapter is in. The cheap `blueprint/parser.py`
   stack can stay as the no-hgraph fallback initially, then be retired too — which also
   dissolves the LaTeX-parsing duplication in §2.3.
5. **Node comments/reviews in the dashboard**: per-node detail view reads the node's
   attachments (already in hgraph's `Entry.reviews[]/comments[]` JSON contract).

## 5. Dashboard performance (measured on OpenGA-Horizon, 162 runs / 2.4 GB state)

A production `/api/state` poll costs **≈ 11–13 s of server work, every 5 s** — the poll
interval is shorter than the compute, so ThreadingHTTPServer stacks concurrent
recomputations. Payload: **17.27 MB JSON (2.15 MB gzip)** re-parsed by the browser on
every change. Measured hot-path offenders:

| # | Offender | Cost/poll |
|---|---|---|
| 1 | Every transcript of every session of every run fully re-parsed (`service.py:410` via `_runs_state`; 2,450 sessions, 396 MB JSONL) | ~5.7 s |
| 2 | `materialize_subagent_sessions` on the READ path (`service.py:409`) — re-reads parents and **rewrites** `subagents/*` files each poll; races between poll threads | ~3.4 s + writes |
| 3 | `events.jsonl` (45 MB) fully parsed **twice** (`service.py:313`, `:191`), no tail-read | ~0.9 s |
| 4 | ETag computed AFTER the full recompute (`app.py:90-92, 161`) — 304 saves bandwidth only | full cost even when idle |
| 5 | 31 MB blueprint JSON re-read + re-stripped per poll (`blueprint/workspace.py:94`, `service.py:53`); 8.96 MB of the payload | ~0.25 s |
| 6 | 1,485 per-item task/roadmap/inbox file loads incl. comments/history | ~0.95 s |

### 5.1 Fixes, ranked

1. **Per-session summary cache**: key `_session_state` on `(path, mtime, size)`; better,
   persist `summary.json` (status/usage/timestamps/model/effort) at session end and parse
   only transcripts lacking one. Completed sessions never change → each poll re-reads
   only the 0–2 live transcripts. Eliminates ~9 s.
2. **Move `materialize_subagent_sessions` to the write path only** (harness end already
   calls it); guard with a marker. Removes reads, per-poll rewrites, and the write race.
3. **ETag short-circuit before compute**: workspace version stamp (max mtime over
   events.jsonl / runs / tasks / roadmap / inbox / blueprints) as the ETag; return 304
   without calling `state()`. Idle polls: ~12 s → ~1 ms.
4. **Tail-read events.jsonl** (seek from end for the 50-event tail), cache by
   (mtime, size), parse once per poll.
5. **Split blueprints out of `/api/state`** (they change only on sync) and cache
   `published_dags` by file mtime — drops 8.96 MB from every changed poll.
6. **Trim runs in the payload**: full session trees for the last N runs only, summaries
   for older ones (fetch on demand); strip bulky session `meta` blobs.

Items 1–3 take a changed poll from ~12 s to <1 s and idle polls to ~0.

### 5.2 UI direction (from hgraph)

Port the hgraph **Overview little-squares** as the default blueprint view: 12×12 px
flexbox cells colored by `lean_status` (single `STATUS` palette source), chapters as
progressive-disclosure `<details>` that re-partition one level finer on expand, each
square clickable to the statement. Add hgraph's **segmented per-chapter progress bars**
(`segbar`) to the project cards. Both are plain flexbox/CSS — trivially portable into the
React frontend, and far cheaper to render than the current DAG-first views.

## 6. Sequencing

- ✅ **Phase A — dead-code sweep** (§2.1(3–5), §2.2): pure deletions + help-text fixes +
  packaged-skill Ground references. −2,401 lines, no behavior change.
- ✅ **Phase B — dashboard hot path** (§5.1 items 1–4): session-state cache (in-memory +
  persisted under `.archon-horizon/cache/`), materialization off the per-poll read path,
  ETag short-circuit before compute, incremental events parse, subtree-stamp caches.
  Measured on OpenGA-Horizon: idle poll ~12 s → ~85 ms (304); changed poll → ~0.5 s;
  restart → ~2 s.
- ✅ **Phase C — orientation & prompt**: CLAUDE.md/AGENTS.md pointers on init; automated
  prompt = task directive + "load the horizon skill"; report shape + model economy moved
  into skills; prompt composition + `.archon-horizon/prompts/` overrides deleted.
- ✅ **Phase D — supervisor**: one `_build_run` launch path; HorizonContext is
  identity-only (no pushed roadmap/inbox/memory); write-domain enforcement removed
  (`core/permissions.py`); the task-terminal watcher kept as the external kill switch
  (2 s poll). *(Deviation from §3.3: the watcher stays — it is the only way to stop a
  live session from outside.)*
- ✅ **Phase E — consumption & limits**: live per-session `usage.json` from the harness
  stream; `horizon usage [--json]`; opt-in `workspace.budget` (session cancel + run
  stop); typed engine-error classification before stderr regex; advertised retry-after
  honored in backoff; `paused.json` marker + exit code 3 on limit/budget stop.
- ✅ **Phase F — HyperGraph**: `blueprint/hgraph_graph.py` adapter (hgraph is a default
  dependency); rich-DAG resolution hgraph → leandag → parser; `hgraph` skill; little-squares
  mini-map + segbar on the Blueprint TOC; `/api/blueprints` split out of `/api/state`
  (19.1 MB → 8.4 MB changed-poll payload). *(Deviation: vendored `leandag/` stays as the
  no-hgraph fallback until hgraph is the everywhere-default.)*
- ✅ **Phase G — dedup (done opportunistically)**: `render/dashboard.py` legacy view
  deleted (no-dist installs get a build-instructions page; the API stays live); store
  construction unified through `build_stores`; inbox author resolution unified through
  `shared.agent_author`. *(Deferred: the full `service.py` reads/writes/dispatch split,
  the shared LaTeX-lexing module, and the inbox shard mixin — lower value, higher churn.)*

## 7. Non-goals (carried forward)

- No parallel sessions; one ledger; plain git (no wrapper); never sleep on a limit.
- Roadmap / tasks / inbox stay three distinct concepts.
- No new database for the graph — hgraph's plain-files model matches the ledger philosophy.
